# Follow-up Suggestion Chips — the *why*

## Problem

Follow-up chips used to be an **optional** model tool (`emit_suggestions`). The
ReAct agent decided per-turn whether to call it. In practice it was wildly
inconsistent — Analyst turns almost never got chips, Advisor sometimes did —
because:

1. The prompt only said *"use when you can suggest natural follow-ups"* — no
   real trigger, pure LLM discretion.
2. The few-shot examples **contradicted each other**: Analyst examples baked
   the follow-up into prose ("อยากดู A หรือ B บอกได้"), Advisor examples called
   the tool. The model copied whichever it pattern-matched.
3. ReAct mechanics: once the model writes a text-only final answer, the loop
   ends — there is no second step in which to call the tool.

## Decision

Make chips **REQUIRED on every non-ADD, non-crisis turn**, generated
**deterministically** instead of by model discretion, with a **locked
"wildcard" slot** so one chip is always a proactive financial-health nudge the
user did not ask about.

- Skipped turns: **ADD** (a transaction proposal was emitted), **crisis**
  (self-harm lexicon — hard code gate), **pure greeting/emotional** or a
  **clarifying-question** answer (the generator LLM self-skips).

## Quick-reply mode — *why a clarifying question no longer kills the chips*

Originally, when the assistant's answer **ended with a clarifying question back**
to the user (e.g. *"รายจ่ายคงที่เดือนละเท่าไรครับ"*), the generator self-skipped:
the whole turn got **zero chips**. The reasoning was sound at the time — chips
are *questions the user asks the assistant*, and you can't stack a question on
top of the assistant's own question without it reading as an echo.

But that left the user staring at a question with no shortcut to answer it. The
chip rail is most valuable *exactly here* — the user knows roughly what to say,
they just don't want to type it. So the generator now picks one of **two modes**
per turn:

- **MODE-NORMAL** (answer is a statement / analysis / advice / greeting) — chips
  are the next **questions** the user would ASK the assistant. The
  ANSWER-LOCATION TEST and TRANSFORM rule apply (a chip is valid only if its
  answer lives in stored data or the assistant's analysis).
- **MODE-QUICKREPLY** (answer ENDS WITH a clarifying question back) — chips
  become the short **answers** the user is most likely to give, so a single tap
  moves the conversation forward instead of dead-ending. Three shapes are
  offered: a reasonable representative value (*"ประมาณ 10,000"*), a "none / not
  applicable" reply (*"ไม่มีรายจ่ายคงที่"*), and handing it back to the assistant
  (*"ช่วยประมาณให้หน่อย"*). In this mode the ANSWER-LOCATION TEST is **disabled** —
  the answer living "in the user's head" is the whole point.

**Anti-misroute guarantee.** A quick-reply chip's `label` is short, but its
`send` MUST carry the **topic** of the question — never a bare number. If a chip
sent just `"10000"`, the next turn's classifier would read it as *"ADD a 10,000
transaction"*. So `send="รายจ่ายคงที่ประมาณเดือนละ 10,000 บาท"` keeps the turn
routed as a continuation (OTHER / advisor flow), not an ADD. This is pinned by
`UT-SG14` (orchestrator emits the chips) and `UT-SG15` (prompt-guard — the
`MODE-QUICKREPLY` + anti-misroute rules can't be silently stripped).

The remaining hard skips are unchanged: **crisis / self-harm** (code-side
lexicon) and **pure emotional venting with no financial angle**. A greeting is
still not a skip.

### The 3+1 formula

| Slot | Source |
|---|---|
| S1 DEEPEN | next rung on the finance ladder (total → category → trend → wallet → budget) |
| S2 DATA HOOK | a notable number / anomaly in **this turn's** data |
| S3 PERSONAL | the user's goals / budgets / recurring behavior |
| **S4 WILDCARD (locked)** | a proactive move (set budget / payoff plan / savings goal), chosen in **code** by the user's data-state — never left to the LLM |

## Where it runs: the `gen_suggestions` graph node

Chips are generated by a graph node — `graph.py::_gen_suggestions`, wired on the
REACT path only, right after react and before the terminal `post_turn`:
`… → react → gen_suggestions → post_turn → END`. The `direct_propose` shortcut
is always an ADD turn (no chips), so it skips the node:
`direct_propose → post_turn`. The node reads the settled answer +
user text from `messages`, the catalog from `user_context`, this-turn tool
output from `tool_outputs_this_turn`, and the ADD signal (a `propose_transaction`
tool call in messages, OR an ADD block in `emitted_blocks_this_turn`), then calls
`build_suggestions_block(...)` and writes the result (block or `None`) to the
`suggestions_block` channel.

This works because **`REACT_IMPL=flat` is the default** — the flat loop
(`flat_react.wire_flat_react`) adds the agent/tools nodes to the *same* outer
builder, so there is no subgraph boundary and a downstream node reads this-turn
channels directly.

> **Historical note.** This used to live in the SSE adapter. The reason was the
> prebuilt-path gotcha: **LangGraph 1.x does not merge a compiled subgraph's
> per-turn channel writes** (`emitted_blocks_this_turn`, `proposals`,
> `tool_outputs_this_turn`) into the parent state for a *downstream* outer node
> — so an outer node saw empty channels. On the dormant prebuilt fallback
> (`REACT_IMPL=prebuilt`) the node still loses raw `tool_outputs_this_turn`, but
> `messages` + `user_context` merge, so answer / catalog / ADD-detection hold.

The **SSE adapter** (`streaming/sse_adapter.py`) is now a **pure forwarder**: it
captures `suggestions_block` off the `updates` stream and emits the `suggestions`
block AFTER the answer block, before `done` — no gating/LLM in the adapter.
**Suggestions are live-only and excluded from history replay.**

The fast-path (`fast_path.py`) has its own SSE emitters and only handles ADD /
clarification — both of which should have no chips — so it correctly bypasses
this entirely.

## Files

- `src/agent/suggest_followups.py` — free-form generator + gates.
  `emit_suggestions` is removed from `ALL_TOOLS` (the `@tool` wrapper is
  retained for direct invocation / legacy tests only).
- `src/agent/graph.py::_gen_suggestions` — the node: reads state signals,
  detects ADD (`_add_turn`), calls the generator, writes `suggestions_block`.
- `src/agent/state.py` — the `suggestions_block` channel.
- `src/agent/streaming/sse_adapter.py` — pure forwarder: emits the node's
  `suggestions_block` after the answer block.
- `src/agent/prompts.py` — `emit_suggestions` tool doc removed; the model is
  told chips are auto-generated and must NOT write a prose follow-up menu.

## Config

`SUGGESTIONS_ENABLED` (default `1`), `SUGGESTIONS_MODEL`,
`SUGGESTIONS_TIMEOUT_S`, `SUGGESTIONS_FALLBACK_MODELS`. On LLM error/timeout a
heuristic fallback still emits the locked wildcard, so REQUIRED holds.
